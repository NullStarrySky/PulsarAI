# PulsarAI Agent Guide

## Hard Rules

- Do not run `bun run build` unless the user explicitly asks for production packaging or build verification.
- Do not run full test suites unless the user explicitly asks.
- When reading files with PowerShell `Get-Content`, always pass `-Encoding UTF8`.
- Prefer scoped implementation, current feature seams, and small verifiable steps.
- When implementing UI components, reuse shadcn-vue components and theme CSS variables whenever practical so spacing, color, radius, focus, and state styling stay consistent.
- Use shadcn-vue `ScrollArea` by default for application-owned scrolling regions such as settings navigation/content, plugin trees, and long resource panels. Its shared wrapper must mount visible vertical and horizontal `ScrollBar` components for overflowing content; keep native overflow only where a specialized editor or virtualizer owns scrolling.
- When implementing or changing components, explicitly consider narrow-window and mobile-platform behavior. Use the shared responsive state instead of scattering viewport or platform checks, keep touch targets usable, and provide an explicit layout fallback below 768px.
- Commands that expose feature behavior to search or hotkeys should keep their implementation in the owning feature's `actions.ts`; UI may register and route commands but should not own domain behavior.
- Plugin files are owned by `src/features/Resources/Plugin`; keep plugin list/workspace/tree controls there and do not reintroduce a generic plugin center page under `src/features/UI`. Each character package owns exactly one package-local resource plugin through `pluginId`, selects one local or global `mainPluginId`, and stores an unordered `enabledGlobalPluginIds` activation set. A main plugin must expose a valid JavaScript `runtime/generatePath`; there is no separate main-context entry. Plugins with `packageId: null` are global. System plugins use `builtIn`, remain editable, and restore from `Plugin/builtIn` source folders. Plugin order and `main` flags must not be reintroduced; equal file `order` values use stable IDs and paths as deterministic tie breakers.
- The Plugin file editor keeps the selected file's single container target, optional JavaScript condition, and container order in its main header, never in a tree-row hover or long-press popover. Depth 0 through 6 are ordinary built-in container choices. Render the file surface inside a centered, bounded, Obsidian-like background card with a full-width fallback below 768px.
- Conversation generation fixes only the outer boundary in `Resources/Conversation/generation/conversation-generation.ts`: create the blank assistant target, build the minimal authorized runtime environment, index visible Plugin containers and data, execute the selected main Plugin's manifest `generatePath`, then bind diagnostics to the target version. `generatePath` return values never become message content; the process writes content, parts, steps, errors, and the actual model name through the target-bound `reply` API. Streaming flows append deltas as they arrive and may read and replace the complete content after the stream for post-processing. There is no main context entry or system-owned context/regex pipeline. The generation process decides which resources and containers to read through `imports`, `run`, and `ctx`, how to build and process context, and whether to call a model. Agent exposes lazy model preparation; custom non-Agent flows must not hydrate a model, and no implicit default-Agent fallback may be restored.
- Conversation resource mutation uses one replayable Overlay. Persist ordered plugin-node `edit/create/move/remove` operations and `.data` instance pure-JSON edits in concrete `ChatMessage.meta.resourceUpdate.operations`, then replay only the active message-version path before building Plugin resolvers and Data facades. Generation-time `write/edit/mkdir/move/remove/config.set` must mutate the Overlay rather than `pluginStore`; do not auto-save individual files during replay or generation. Updater-enabled `.data.json` definitions keep isolation, initial value, wrapper, description, updater, and optional `varName`; the wrapper operates on persisted pure JSON and emits the same Overlay edit operation instead of a special variable-update source. `codeAct` remains the only model tool, has no variable-update intent, and commits all file/Data operations from one successful call atomically; a failed call restores both Overlay views. `import` and `run` lazily preparse Data against the replayed Overlay. Data wrappers must return exactly one object facade. Plugin-root creation, movement, and deletion stay outside the Conversation Overlay.
- Compression memory is derived immutable Conversation data. A resource that uses compression reads `compressionThreshold` from Plugin configuration explicitly; there is no privileged context entry. Keep recent containers raw, persist leaf pointers with exact container/message-version identities, allow higher pointers to index adjacent lower pointers, validate the complete pointer chain against the active path, and fall back to raw chat with diagnostics on compression failure. Do not rewrite message content or branch topology; delete derived segments with their conversation.
- Conversation message failures use `ChatMessage.type: "error"` rather than a new AI role. Normalize every error message body with a single `[ERROR]` prefix, keep it visible and persisted, render it as a destructive alert, exclude it from both `chat` and generation `activePath`, and expose explicit insertion through the authorized `conversation.pushErrorMessage(content)` capability.
- Message favorites belong to concrete `ChatMessage` versions. Keep map search scoped to the current conversation, rank favorite matches first, and route both map results and the Conversation-owned favorite settings page through the shared version/branch activation and renderer-jump path.
- The main Plugin manifest stores the model override only at fixed `generation/model`. Chat model references use `provider/modelId/thinkingLevel`; the final thinking segment is optional, and only recognized AI SDK reasoning values are stripped from the model ID. When present, pass it through AI SDK 7's top-level `reasoning` option; otherwise omit that option and expose `auto` to the Sandbox as `reasoningEffort`. Background selection belongs only to the built-in Plugin's fixed `appearance/background` value. It stores an extensionless Plugin-relative path ID selected from the `background` container; when resolving that ID, prefer the current package-local Plugin resource before global and built-in resources. Model and thinking choice stay out of Conversation persistence and share the single ModelSelect control.
- Public Feature APIs are always present in the Sandbox at `<featureId>` and `capabilities.<featureId>`; they are fully included by default. Keep each feature's API documentation metadata in the owning feature's root `docs.ts` (pure metadata, no runtime imports), expose the shared catalog through `read_docs()`, and inject only the short `read_docs` bootstrap instead of the complete API reference. The registry (`src/features/Capabilities/registry.ts`) wires the runtime API objects and removes only explicitly classified destructive, external-side-effect, paid, or arbitrary-execution methods from the actual runtime object rather than merely hiding their documentation. There is no per-feature `capabilities.ts` and no sub-capability grant system; do not reintroduce them.
- The standard conversation list uses dynamic-height TanStack virtualization. Keep logical message counts and total virtual height visible to `MessageScroller`, measure every mounted row, and route off-screen message jumps through the virtualizer before relying on DOM lookup.
- Interactive chat code previews are controlled by the persisted Appearance setting `interactiveCodePreview` (default off). When enabled, only recognize fenced blocks containing `<html>`, `<!DOCTYPE>`, or `<script>`, run them in `srcdoc` iframes without `allow-same-origin`, replace the latest active message body with its preview, and preserve a source-view escape hatch.
- Reversible translation metadata belongs to the concrete `ChatMessage` version under `meta.translation`. Clear stale translation snapshots on manual edits and restore through the Conversation store rather than presentation-only state.
- Conversations always belong to a user character package and use `Conversation.kind` (`chat` or `test`) for hard semantics. Persist only stable resource relationship IDs in `Conversation.binding`; resolve mutable titles, paths, and owning packages at read time. Do not introduce a system character package as a storage bucket.
- CharacterPackage may store an optional stable `nickname` as a source-facing alias. SillyTavern character imports use the original card filename without its extension; resource ownership and navigation must continue to use stable IDs rather than nickname matching after import.
- External prompt syntax is converted only inside `src/features/Migrations`: simple non-nested SillyTavern macros and synchronous ST-Prompt-Template EJS become ordinary `{{ JavaScript }}` expressions through the shared source converter. Do not add a SillyTavern/EJS parser, event bus, API mock, or compatibility globals to Sandbox execution. Unsupported scopes, flags, nested macros, async EJS, includes, DOM/UI calls, and foreign APIs are replaced with inert JavaScript comments plus migration diagnostics.
- The focused conversation shell owns character-package and conversation selection in its header. `PluginAssetTreePanel` renders package-local, global, and built-in plugins as an overlay asset panel, and selected files open in `PluginFileEditorDialog`; do not reintroduce workspace tabs, shell sidebars, or generic resource-page registries. Plugin tests are database conversations with `kind: "test"` and a plugin binding, never message-history files inside the plugin tree.
- Conversation renderers are selected per `Conversation` through `rendererId`. Keep renderer UI under `Resources/Conversation` (stage/composer/map/pages layout); templates persist this field and new conversations inherit it when their message path is cloned.
- Plugin contents are a nested `root` file tree backed by stable database nodes. Derive ordinary file semantics from suffixes, but select convention-file editors and runtime roles by exact paths. `info.md` has no special meaning. Use optional `AGENTS.md` for free-form Agent instructions, `manifest.json` for configuration and `runtime/generatePath`, `containers.json` for declarations, root `regex.json` for rules, `*.chat.json` for role-aware messages, and `*.data.json` for reusable data definitions. `tools/<name>/tool.js + prompt.md`, `components/`, `action/`, `background/`, and `temp/` keep their documented conventions. There is no main context entry. Do not add implicit fallback entries or automatic plugin-tree rewrites.
- Plugin persistence uses `resource_plugins` for plugin metadata and `resource_plugin_nodes` for stable tree nodes. Keep node identity, parent relationship, path, `treeOrder`, file `order`, optional single `insertion`, and content in SurrealDB; rebuild paths and search fields transactionally on plugin writes. Global search must query plugin metadata plus the database-backed node path/name/content index and navigate by stable plugin/node IDs. Do not store the complete plugin tree in `resource_plugins` or introduce a second source of truth.
- Plugin resources never become ambient Sandbox variables. Markdown macros and Plugin JavaScript use ambient top-level FS functions (`read`, `write`, `edit`, `ls`, `exists`, `mkdir`, `move`, `remove`, `import`, `run`, `test`, `test_condition`, `grep`) and URI path prefixes (`@/` for local plugin, `@<pluginId>/` for target plugin). `import` parses and expands text/macros without code execution; `run` explicitly executes `.js` scripts. All environment parameters accept a `conversationId` string for IoC context injection or an explicit environment object. Container operations are namespaced under `container.*` (`list`, `get`, `read`, `import`, `test_condition`), and config operations under `config.*` (`list`, `get`, `set`). Literal arguments to `import("@/...")`, `container.import(...)`, and `config.get(...)` power static discovery, while runtime resolution remains authoritative. `test` supports AST trace diagnostics and context truncation (`textTruncateLength`, default 20); `test_condition` and `container.test_condition` evaluate JavaScript condition rules with structured `ConditionResults`. Container scope is only `local` or `global`. Container declarations belong to root `containers.json`. A file has at most one explicit string insertion target with an optional synchronous JavaScript condition; its list editor composes AND/OR rules and the runtime supplies `include`, `exclude`, `probability`, and ambient FS/container capabilities. Message depth uses built-in IDs `depth:0` through `depth:6`. Container membership only registers a resource and never causes generation automatically. Container members use `<pluginId>/<plugin-relative-path>`; the editable plugin ID is the top-level path segment, so same-named files in different plugins do not collide. Importing `.data` returns its hydrated wrapper facade. Containers remain lazy namespaces and must report duplicate plugin IDs, duplicate in-plugin paths, missing imports, invalid JSON, and cycles instead of applying last-write-wins merges.
- Plugin container declarations include stable `id`, localizable `title`, `scope`, one-line `description`, `contentSuffixes`, `selectionMode` (`single`/`multiple`/`none`), `overrideStrategy` (`override`/`merge`/`intersection`), and optional `selectedPaths`. Keep them serialized in root `containers.json` and available to completion with owning-plugin context. Container import and resolution filter resources according to selection mode and strategy, and path arrays are exposed via `container.paths(...)` / `readContainerPaths(...)`. Titles and descriptions are authoring metadata and must not enter generation automatically.
- Container inspection and generic reading must reuse `plugin-reference-resolver.ts` so `containers.json`, `ctx`, and Plugin APIs report the same enabled topology. Containers own no extractor, transformer, template, Skill adapter, or execution policy. Keep resources navigable through `container.list`, `container.get`, `container.read`, `container.import`, and `container.paths`, retaining stable IDs, paths, sources, and order. Declarations stay in `containers.json`; explicit membership stays on file insertion metadata.
- Plugin files persist an independent numeric container `order`, defaulting to `100`; equal values use stable Plugin and resource IDs as deterministic tie breakers.
- Plugin background files use media content (`kind: "media"`), live under the conventional `background/` folder, and explicitly register in the `background` container with `selectionMode: "single"`. Background selection is powered by container single-choice selection (local overriding global) instead of `manifest.json` options. Keep media parsing, preview, selection, and built-in background assets under `Resources/Plugin` rather than encoding backgrounds as CSS snippets.
- Conversation actions are JavaScript or Markdown files under `action/`. JavaScript commands keep the leading `ActionPart`, add `action` and `prompt` to the minimal Sandbox, and temporarily replace the current `generatePath`; they have no return value, and errors are thrown and surfaced through Notivue `push`. JavaScript commands create hidden command containers carrying their invocation and a command-local `draft.md`; the containers remain on the causal/replay path but must be excluded from ordinary chat and compression prompts, while their collapsed panel remains inspectable in the thread. The command sandbox exposes that scratchpad as `ctx.draft.read()` / `ctx.draft.edit(find, replace)` and virtual `read("draft.md")` / `edit("draft.md", find, replace)`. Markdown commands only replace the composer draft and never create a message.
- A file insertion may use either its inline synchronous JavaScript condition or `conditionPath`, a Plugin-relative JavaScript resource whose evaluated result is synchronously coerced to boolean. The path resolves relative to the declaring resource and is evaluated in the same condition environment; it must not implement scheduling or delayed execution itself.
- Enabled root `regex.json` files register in the ordered `REGEX` container. Generation does not apply them automatically: `generatePath` decides whether and when to read and execute them. Conversation rendering may reuse rules with `applyOnRendering: true`, but must never persist rendered replacements back into message content.
- `codeAct` is the only model-visible tool. It must accept one JavaScript function with an explicit `return`, execute it against the authorized Sandbox environment, and return either the function value or a structured error to the model. Keep Feature APIs, Plugin APIs, ask-user, Skill, and MCP operations as callable context functions instead of adding parallel AI SDK tools.
- Plugin custom tools remain ordinary Sandbox functions, never additional AI SDK tools. Discover only immediate `tools/<name>/tool.js` functions that also have `prompt.md`, order them by descending `tool.js` order and stable plugin/resource keys, reject name collisions, expose them as `ctx.tools[name](...args)`, and inject one `# 自定义工具` system block containing each prompt plus plugin/resource IDs and paths.
- Skill and MCP integrations remain registered through `Agent/runtime/agent-extension-registry.ts`, but CodeAct calls them through context APIs such as `agent.callExtension(...)`, `skills.call(...)`, or `mcp.call(...)`; do not create a separate conversation generation path for either feature.
- Ask-user input and normalization are owned by `Agent/runtime/ask-user-tool.ts` and pause CodeAct through the Conversation generation-component requester. Keep question UI registered as `agent.ask-user`, and expose it through `agent.askUser(...)` / `api.askUser(...)` instead of a second model tool or parallel chat protocol.
- Role-aware context resources are Plugin-owned `.chat.json` files containing `{ message: Array<{ role, content }> }`; the Plugin workspace provides their structured editor and source mode. Sandbox expressions use the same source-scoped `imports` facade as JavaScript. Data definitions are Plugin-owned `.data.json` files that declare isolation, initial value, wrapper, description, and updater behavior internally. Do not reintroduce Preset or InteractiveDoc Features.
- Version management is owned by `src/features/Backup`. Keep full-database disaster restore separate from selective resource restore, store new history snapshots as manifests over the shared SHA-256/Zstandard object repository while retaining legacy directory-backup reads, and remap parent and child IDs together when importing resource copies. Portable package, conversation, and plugin archives use stable IDs; update mode must diff and merge domain relationships while preserving conflicting message versions and plugin files. Keep LAN version metadata in `src/features/Database/sync-metadata.ts`.
- Settings navigation is a flat page registry with Hotkey first; a page may expose first-level functional tabs. `SettingsDialog` owns the visible page title, tabs, search, close action, and desktop drag surface, while `SettingPage` owns only scrollable content. Reuse `SettingForm` and `SettingFormField` whenever practical; groups have no description or card border, while each field keeps its own title, description, and control area.
- Feature API documentation exposed to generated JavaScript lives in the owning feature's root `docs.ts` as a `FeatureDocs` object (id, title, description, optional human documentation, flat `api` list). Keep human `documentation`, documented types, API signatures/descriptions/examples, runtime methods, `read_docs()` output, and blocked-method status synchronized. `src/features/Capabilities` owns aggregation (`docs-index.ts`), runtime wiring plus the on-demand blocklist (`registry.ts`), and Markdown generation (`docs-markdown.ts`); VitePress must generate its human Markdown and outline from these definitions instead of maintaining a second API inventory. `docs.ts` files must stay import-free of runtime stores so scripts and VitePress can load them without side effects.
- Conversation composer toolbar placement is owned by the UI appearance store as normalized `left`, `right`, and `unused` arrays. New composer tools must be added to the shared toolbar catalog and receive a migration/default placement instead of being hard-coded into the workspace footer.
- The Conversation composer `map` tool renders the current conversation's `ChatMessageContainer` tree without merge edges. Keep graph layout and node navigation under `Resources/Conversation`, activate every ancestor branch before jumping, and use the shared toolbar catalog for placement.
- Native and built-in notifications go through `features/Notification/notification-service.ts`; external delivery is the default, while `channel: "internal"` writes to the built-in notification center.
- `layout-store.ts` owns only shared settings visibility and immersive-conversation state; resource navigation belongs to the focused Feature surface rather than generic workspace tabs.
- Main-window close behavior is generic UI lifecycle state owned by `UI/window-lifecycle-store.ts`. Intercept close requests only for the `main` window; subwindows close normally. The native desktop tray only restores/focuses the main window on left click and exits from its context menu.
- `todo/main.todo` is the backlog index and references focused plans in the same folder. Treat them as project context when planning feature work, but do not delete completed or skipped items unless explicitly asked.

- The Conversation Feature owns the unified `conversation.requestContainer(...)` lifecycle. Its `generate` and `command` modes create and run a new ordinary or hidden command container; `regenerate` adds and activates a new version in an existing ordinary assistant container; `continue` and `rewrite` mutate its current version in place. Generation paths must use this request helper rather than constructing empty assistant or command containers ad hoc. Hidden command containers have exactly one version and must reject version switching/addition/deletion plus regenerate, continue, and rewrite.
- WebSearch owns its provider settings page and exposes only bounded search results. Playwright is the desktop browser provider; Exa Search API is the Secret-backed online provider, with `exa-js` retained as the TypeScript API contract while native Rust injects the key. Do not reintroduce Selenium, WebDriver, arbitrary browser execution, or a browser fallback path.

## Project Shape

Pulsar is an open LLM frontend built with Tauri, TypeScript, Vue 3, shadcn-vue, AI SDK, SurrealDB, and Milkdown.

`src/features/TTS`, `src/features/STT`, and `src/features/ImageGeneration` own pure media-service entrypoints and settings pages, never Conversation or message lifecycle. Keep AI SDK-capable multi-model platforms in ModelConnection and let these Features reference the corresponding speech, transcription, or image models with shared secrets. Keep only lightweight speech-service adapters such as Edge TTS, Volcengine OpenSpeech TTS, ElevenLabs, Azure Speech, and native OS TTS inside the owning Feature. Volcengine, ElevenLabs, and Azure credentials must remain Secret placeholders injected by the Rust model proxy; do not read them into frontend state. ElevenLabs and Azure may share their provider credential across TTS and STT adapters, but each Feature owns its own pure service implementation and neither may introduce voice-history, cloning, upload, conversation, or message lifecycle into the basic generation path. Native playback/recognition services that do not return media bytes or accept an input media file must expose honest service entrypoints instead of pretending to implement AI SDK `SpeechModel` or `TranscriptionModel`. `tauri-plugin-stt` is mobile-only in Pulsar: register its iOS/Android system engines, but never compile or expose its desktop whisper.cpp/GGML path. Do not expose providers marked `runtime: "local-heavy"` or otherwise requiring large local models, standalone daemons, complex hardware, or a substantial local runtime until the local-runtime phase; flag them to the user instead. Only surface fetched models when the owning ModelConnection adapter can assign the explicit `tts`, `asr`, or `image` capability; never guess media capability from a generic `/models` response. Their settings reuse ModelConnection's compact provider-name popover, including per-provider activation switches, without custom-provider creation or model editing/tag UI, while provider-specific parameter forms remain flexible and tests must generate real audio, transcripts, or images. ComfyUI (including RunPod Serverless) and AUTOMATIC1111/Forge are explicitly approved exceptions to the current `local-heavy` deferral: keep them as ImageGeneration-owned connection-only services with real connection tests and user-controlled endpoints; PulsarAI does not own their daemon, worker, model, or extension lifecycle.

The frontend organizes code under `src/features`, one folder per feature. There are no DDD layer folders (`application/`, `domain/`, `presentation/`, `infrastructure/`): keep small features flat at the feature root, and give larger features content-named folders that describe what the files are (for example Plugin's `tree/`, `editors/`, `runtime/`, `shared/`; Conversation's `store/`, `generation/`, `messages/`, `stage/`, `composer/`, `map/`, `pages/`; provider adapters in `providers/`; Vue components in `components/`). Do not reintroduce layer-named folders. Every feature keeps its public API documentation in a root `docs.ts`.

`src/features/UI` owns only the shell and generic application dialogs. Feature-specific surfaces live in their owning Feature and are composed directly by the focused conversation shell.

## Current Phase

The app is moving through the basic agent and conversation-runtime phase:

- one minimal conversation shell;
- model provider settings and default model selection;
- local SurrealDB-backed settings and secrets;
- AI SDK wrappers that hydrate provider/model references;
- an editable built-in plugin workflow that uses the Conversation-bound `new agent.ToolLoopAgent({ container: reply })` wrapper; it alone prepares the AI SDK model/tools and fills the target container;
- a frontend sandbox for macro expansion and controlled JavaScript execution;
- Feature API docs (`docs.ts` per feature) aggregated by the Capabilities registry, which fully includes each API and applies one on-demand blocklist for dangerous methods, feeding `read_docs()` and VitePress from the same definitions;
- appearance, font, and about settings;
- Milkdown/Crepe markdown rendering for messages and composer input;
- plugin file trees as focused asset-panel resources with scoped lazy containers, explicit references, and no duplicated composer selector;
- role-aware Markdown documents plus metadata-bound reusable `.data`, Milkdown editing, and compiled context messages;
- built-in settings and schedule surfaces composed directly by their owning dialogs rather than a generic workspace registry;
- SubWindow protocol and WebviewWindow adapters isolated under `src/features/SubWindow`;
- `design.md` as the project index.

MCP, Skill, and richer tool orchestration are later-phase additions.

简明PulsarAI系统设计概览：
目标：
基于尽可能少的基础设施，构建提示词组装和agent流程控制系统，提供尽可能强大的功能和灵活性。
为了这两者，我们不太考虑安全性。
思路：
以下是其它系统的设计：

# 阶段1：无
考虑最简单，无扩展性的系统是：
将chat直接发送给模型，然后将回复写入。

# 阶段2：系统提示词
一些项目允许用户定义系统提示词，其将插入到chat之前。

# 阶段3：系统提示词+静态宏系统
更进一步的，一些项目允许用户使用类似 {date}，{content}等
这些静态宏被解析到系统中的一些默认配置，或者动态元素中

# 阶段4：系统提示词+含参静态宏系统
某些项目中，宏系统被扩展以支持参数，譬如 {{roll::2d6+3}}

# 阶段5：消息模板+含参静态宏系统
在酒馆这样的项目中，不使用系统提示词，而是使用类似消息数组的方式管理上下文
此数组中的部分元素被替换为特定的，不可编辑的系统提示词区段，这些特殊区段作为一系列消息的位置。

然后我们开始pulsarAI的设计：

# 阶段6：动态宏系统
出于最大化宏系统的灵活性（我们可以牺牲一些安全性）和简洁性的需要，
我们使用动态宏系统，即：每一个宏都是一条会在特定的 环境对象 中求值的JS表达式或者函数体，允许异步。
我们使用{{}}语法，其将编译结果转换到字符串并内联。
{{ 1+1 }}会被编译成2，{{ date }}在{date: ()=> '2002-10-01'}中被编译成'2002-10-01'
特别地，如果内容是数组，我们使用array.join('\n')，这是为了避免代码插槽执行错误。

类似酒馆中的插槽，为了插入一系列消息，我们允许[[]]语法。
其类似{{}}，但如果编译结果是一个数组，那么，其撕裂所在的元素，将数组展开。
具体地，如果父元素是单纯字符串，将其变成包含它的撕裂后的数组，将自身元素变成字符串，然后flatmap进去，获得结果数组。
如果父元素是数组中的字符串，将结果数组也flatmap进去。
hi, [[ a ]], good morning.
在{a: ['alice', 'bob']}中，被编译为：['hi, ', 'alice', 'bob', ', good morning.']
此功能用来覆盖酒馆中的区段，并保持了消息数组的类型一致性。

动态宏系统的两个语法是系统中唯二的静态语法。

并且，沙箱提供了循环解析api，其并发的解析输入中所有的宏，直到发现循环或者没有宏，给出最终结果（或者附加解析栈的解析错误）
每次触发批量解析的时候，此api将相应的结果压入logger中，组织成一棵树，如果发现相同的宏解析或者解析轮数过大，就说明是循环。
（理论上可以通过动态执行write构造出不同宏内容-宏结果的无限循环，停机问题无法判别，尽量即可）

# 阶段7：动态宏系统 + 文件树
我们得谈谈资产管理了。
大部分项目没有资产管理一说，即使有，也是不参与上下文构建的“工作区”，其映射到一个外部文件夹之中。
酒馆采用按照类型分类（而非按照包分类）的系统，设计的相当扁平且混杂，无分类，非常烂，在此不再赘述。
PulsarAI采用文件树管理资产体系。
PulsarAI中，允许若干个角色包，每个角色包持有自身的若干个会话，以及一个唯一的自身插件。
PulsarAI中也允许全局插件。
每个插件都是一颗文件树，这种做法提供了最大的资产组织灵活度。
并且，我们允许指明一个全局插件是“主要”插件

那么，如何将这些资产应用到提示词构建之中呢？
在文件树中，我们提供read, edit, write, ls等文件api。
并且允许使用@/前缀来引用本插件内资源。
不过，对于提示词构建而言，我们一般仅使用import api。
其基于路径返回资产内容的同时，基于资产类型对资产进行包装。
比如，import('@/data.json')返回的是json对象，从而允许我们取其子内容，而非像read那样返回字符串。

一般的，一个提示词构建的入口是一个.chat.json文件，其结构为消息数组，但添加了额外的，标记开关和名称的字段。
其中包含了形如：
{{import('@/character/alice.md')}}
{{import('@/data.json').key}}
的宏
并且，这些被引用的文件中，也可能包含这样的宏，即宏是嵌套的。

我们在沙箱中构造合适的环境对象，然后对其进行宏解析循环。
此种架构在尽可能简洁的同时，允许对资产的任意后处理，允许任意合法js作为宏控制语句。

# 阶段8：动态宏系统 + 文件树 + 插槽
上述架构未解决的问题是扩展性。
出于扩展性的需求，我们引入插槽机制，每个插槽代表一个可以用于资源注册的注册表。
其可用于生成流程，上下文组装，或者系统中其余需要通过插件扩展的位置，比如会话的背景图片或者指令。
插槽声明于每个插件的slot.json，其内容为：
名称，id，描述，本地/全局
单选/多选/无选择性，选中的资源

资源可以声明自己所属的插槽，以及自身的优先级和插入条件（同样是js表达式，由import处理）
插槽就等于资源的位置，或者说类型。
插槽自身，全局插槽允许全局资源插入，本地插槽只允许本插件资源
选择性允许插件决定自身具体使用的类型以覆盖全局选择

在运行时，我们收集开启的插件中的插槽定义，内容，以及选择性。主要插件中的插槽选择性视为全局选择性。
在宏系统中，我们可以使用：
{{slot.import('character')}}
来引用插槽。
其被解析为若干连续的
{{import('$pluginid/character/xxx.md')}}
（从而复用import的日志写入）

插槽系统也适用于生成流程。
即，我们允许插件中包含基于引用和插槽的.js文件，也允许js文件中直接调用slot api来获取插槽内容。
从而，我们可以像控制上下文那样，组装生成流程。
譬如，在ctx_builder插槽中，向ctx中注入函数，并且在data插槽中注入函数的定义。
从而允许模型使用codeAct运行此函数，当然，codeAct也执行在环境对象中。

环境对象中一般包含会话注入的chat对象以及相关api，系统其他附属组件注入的api，插件的文件树api，资产条件判别用的一些内置函数
以及若干工具性的函数和字段。

# 阶段9：动态宏系统 + 文件树 + 插槽 + Overlay
这不是核心，但有必要谈谈。
不同于其它的项目，我们的项目提供真正的会话分支（而非复制），以及历史消息的重生成能力。
我们讨厌冗余。

会话是一颗树，每个节点保存其父母节点，子节点（分支）数组，以及其具体指向的子节点。
每个节点中包含若干个对应了本地重生成的等位消息以及具体消息的索引。
为了保证分支切换时候的状态正确性，在agent调用插件api进行文件写入的时候，我们会计算插件系统的具体的变更
并且将其以create, edit, move, delete的方式绑定到消息，其和初始插件作为事实来源，重放出来的最终插件状态作为生成源。
当然，用户也可以类似git push那样把一些当前状态写回到原始插件中。
这种机制允许不同的会话共享同一个长期记忆插件，它们持有各自的插件演变，而插件本身提供的契约保持唯一。
